# Driver loops stop gating cancellation/polling on subprocess stdout

`Discovery`/`Capture`'s background driver loops (`_drive` in `discovery.py`/`capture.py`) no longer iterate `handle.lines()` to drive cancellation checks, CSV polling, deauth bursts, or handshake checks. Each is now a plain wall-clock `while` loop, ticking every `tick_interval` (new `DEFAULT_DRIVE_TICK_INTERVAL`, 0.5s, injectable) regardless of what the spawned tool's stdout is doing, using a new non-blocking `ProcHandle.poll()` method to detect the process dying on its own. `_RealProcHandle` now always drains stdout into a bounded background queue too (same treatment stderr already had), so an unread stdout pipe can't deadlock the child even though nothing reads it for these two drivers' main handle anymore.

## Why

Discovery's "no networks ever show up" bug turned out to be three independent bugs stacked on top of each other, each hiding the next until the previous was fixed:

1. `SudoSession.run_privileged()` passed `start_new_session=True` to every privileged `Popen`, which calls `setsid()` and puts the child in a brand-new session every single time. With no `tty_tickets` override in this machine's sudoers (the compiled-in default applies: the cached sudo credential is scoped to the calling tty-or-session), every privileged call landed in a never-before-seen session and could never see the credential `SudoSession.start()` had just cached — so `sudo -n` failed with "a password is required" on literally every privileged call, regardless of password correctness. Fixed by switching to `process_group=0` (Python 3.11+; this repo runs 3.12), which gives the child its own process group (preserving the `pid == pgid` guarantee `terminate()`/`kill()` need) without creating a new session. Confirmed directly, not assumed: demonstrated the session-id divergence with a harmless Python subprocess test before touching any code.
2. `Discovery._drive` spawned `airodump-ng --write-csv <prefix> <adapter>` — not a real flag (confirmed against `airodump-ng --help`; the real one is `--write`/`-w`, with CSV already part of its default `--output-format` set). Real airodump-ng rejected it with "unrecognized option" and exited instantly, which nothing checked, so this looked identical to "ran fine, found nothing" since the start. See `docs/roadmap.md` Phase 1 item 0's own "Revisited" note.
3. Even with both of the above fixed, the database still never gained a row. Root-caused with two standalone repro scripts (not assumed): real `airodump-ng`, run through `sudo` with a piped (not file-redirected) stdout, can stop producing stdout output indefinitely after its very first line, while the process keeps running and keeps writing its CSV file correctly the whole time. Forcing `--background 1` (airodump-ng's own "override background detection" flag) did not change this. Most likely cause: `sudo` allocates a pty for the child, and a curses-style full-screen redrawing tool can hang against a pty with no real terminal behind it — not fully root-caused at the kernel/sudo level, but the stall itself was reproduced directly and repeatedly, independent of this app's own code. `Discovery`'s loop (and `Capture`'s, which shares the identical shape against the same tool, though not yet hardware-triggered there) treated "no new stdout line" as indistinguishable from "nothing to do" — so once stdout stalled, cancellation checks, CSV polling, deauth bursts, and handshake checks all silently stopped forever, with the underlying process running unattended.

Bug 3 is the one this ADR is about: a job-driver loop's own liveness/cancellation/polling must never depend on a spawned tool's stdout being reliably chatty, since that's an assumption about the tool's own internals and its interaction with `sudo`/ptys that this codebase doesn't control and can't guarantee holds on every adapter, driver, or distro.

## Considered Options

- **Fix the `sudo`/pty interaction directly** (e.g. disable `use_pty` in sudoers, or rely on `--background`). Rejected — `--background 1` was tried directly against the real stall and didn't fix it; a sudoers-level change is a system security policy change outside this app's own control and isn't guaranteed to generalize to every machine AirCommand runs on, unlike a self-contained code fix.
- **Keep the stdout-driven loop, add a watchdog that force-polls if no line arrives within N seconds.** Rejected — still structurally depends on stdout for its normal-case timing signal, just adds a fallback path for the abnormal case; more moving parts for no real benefit over not depending on it at all.
- **(Chosen) Decouple entirely: a wall-clock loop drives all periodic work, `ProcHandle.poll()` (non-blocking) replaces "the stdout loop ended" as the liveness signal, and stdout is drained in the background unconditionally (bounded, discard-on-full) purely to prevent an unrelated failure mode — the pipe filling up and blocking the child's writes — without the loop ever depending on that content.** No dependency on the spawned tool's own stdout behavior, chatty or not.

## Consequences

- New `ProcHandle.poll()` on the shared subprocess protocol (`procutil.py`) — any future long-running driver should prefer this over `.lines()` for its own cancellation/liveness checks if it has periodic work to do that shouldn't depend on the tool's stdout cadence.
- `DEFAULT_DRIVE_TICK_INTERVAL` (0.5s) is the standard wall-clock cadence for driver loops now; `Discovery`/`Capture` both take it as an injectable `tick_interval`, threaded through `Engine`'s own `drive_tick_interval` constructor param.
- `Crack`/`Enumerator`/`rf.py`'s one-shot and short-lived calls were deliberately left untouched — they still use `.lines()`/`.wait()` directly, since their own output is what they actually need and they aren't continuously-redrawing interactive tools subject to this exact stall shape. Not blindly "fixed" to match a pattern that doesn't apply to them.
- `_RealProcHandle` now background-drains stdout unconditionally (mirroring the existing stderr treatment), through a bounded (10,000-line) queue with discard-on-full for the content, but a guaranteed (blocking) delivery of the EOF sentinel so an actively-consuming caller (`crack.py`'s hashcat `--status-json` stream, `enumerate.py`'s nmap XML, `rf.py`'s drains) is never left waiting forever. The bound exists specifically because Discovery/Capture's own long-running `airodump-ng` handle never calls `.lines()` at all — on hardware where this tool's stdout doesn't stall (not guaranteed, just this machine's observed reality), an unbounded queue would otherwise grow for the whole session with nothing ever consuming it.
- Verified end-to-end on real hardware after all three bugs were fixed: Discovery's network table populates correctly from a live scan.

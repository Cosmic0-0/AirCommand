# Discovery band-gating, revised: unchosen default, Start gated on an explicit pick

Amends ADR-0013's default/gating decision (point 5 of its Decisions list) in response to the approved Grid Watch × Wireframe A handoff (`docs/design/gui-redesign-gridwatch.md` §0 item 2, §6 item 4). ADR-0013's band dropdown defaulted to the most inclusive supported choice, pre-selected, with Start Discovery simply enabled once Idle. The reviewed design instead wants the dropdown to open on a disabled placeholder ("Choose a band…") with nothing pre-selected, and Start Discovery additionally disabled until the operator explicitly picks a real band. Everything else ADR-0013 decided — the `iw phy <phy> info` capability query, `DiscoveryOptions.bands`, the derived Band column, no-auto-start, dropdown choices filtered to what the adapter supports — is unchanged.

## Why

ADR-0013 optimized for "get Discovery scanning with as few clicks as possible" (most-inclusive default, no extra gate). The handoff's own review feedback (item 4) wants the opposite: force the operator to look at and choose a band before the first scan, rather than silently inheriting whatever the most-inclusive default happens to be. Both are legitimate defaults for the same control — this amendment records which one the operator actually picked for this GUI, and why, rather than letting the new behavior silently overwrite the old ADR's stated reasoning with no trace.

## Decisions

1. **This is a GUI-layer change only — no core file changes.** `DiscoveryOptions.bands`'s dataclass default (2.4GHz) is never actually reached through the GUI path either before or after this change, since `app.py` always constructs `DiscoveryOptions(bands=...)` explicitly from whatever the dropdown currently shows before calling `discovery.start()`. `supported_bands()`, `BandUnavailable`, `parse_iw_phy_bands`, and the Band column are all untouched. Scope is entirely `aircommand/gui/app.py`'s `_build_discovery_targets_tab`/`_start_discovery`/`_on_discovery_stopped` and the band-menu construction.
2. **The band menu's values gain a leading placeholder, "Choose a band…", which is never a usable choice — only a sentinel meaning "nothing picked yet."** `self._band_menu` is built with `["Choose a band…", *real_choices]` and starts `.set()` to the placeholder string, never to `real_choices[-1]` (ADR-0013's old default). `self._band_choices` (the label → `frozenset[Band]` map) does not gain an entry for the placeholder — looking it up by the placeholder's label must never happen, because Start/Resume/New Session are disabled whenever the menu reads it (point 3).
3. **Start/Resume/New Session are enabled iff the band menu's current value is not the placeholder — re-evaluated on every band-menu change, not decided once per session.** A new `_on_band_menu_changed` callback (wired via `CTkOptionMenu(..., command=...)`) flips the Start/Pause-Resume button and New Session button between enabled/disabled based on this check alone. Once the operator picks any real band, the buttons enable and **stay** enabled for the rest of the session — the placeholder is never re-selected programmatically (it stays in the dropdown's value list, but nothing in this GUI's own code ever calls `.set()` back to it), so this is a one-time gate in practice, not a per-Pause reset, even though it's implemented as a live, re-checked condition rather than a one-shot latch. This also means a single-supported-band adapter still requires one explicit click before Start enables — consistent behavior regardless of how many real choices exist, rather than special-casing the single-choice case to auto-select.
4. **The Idle-state Start button's initial `state` is `"disabled"`, not the current unconditional `"normal"`.** Matches point 3: at construction, the menu reads the placeholder, so Start starts disabled. This is the one concrete code-level deviation from the existing `_build_discovery_targets_tab` — today's `ctk.CTkButton(..., text="Start Discovery", ...)` has no explicit `state=` (defaulting to normal); it needs `state="disabled"` until the first real pick.
5. **A single-supported-band adapter's dropdown is still interactable for the one real choice, even though ADR-0013 permanently disabled it when `len(self._band_choices) <= 1`.** ADR-0013's reasoning for disabling a single-choice dropdown ("nothing to choose") no longer fully applies: the operator must still interact with it once, to move off the placeholder and satisfy point 3's gate. The dropdown becomes enabled whenever there is at least one real choice AND no scan is running (Idle/Paused) — point 3's own gate is what makes a single real choice still meaningfully clickable, replacing ADR-0013's `len(...) > 1` condition with `len(...) >= 1` for the *enabled* check specifically (the *disabled-while-scanning* half of ADR-0013's state table is unchanged).

## Considered Options

- **Reset the dropdown back to the placeholder on every Pause, forcing a fresh pick before every Resume.** Rejected — nothing in the handoff asks for this, and ADR-0013's own state table already lets the dropdown stay at whatever it was showing through a Pause/Resume cycle; re-litigating that per amendment would be a bigger behavior change than the handoff's review feedback actually describes (item 4 only talks about the *initial* default and the *first* Start gate).
- **Auto-select the sole choice for a single-supported-band adapter, skipping the explicit-pick gate in that case.** Rejected — inconsistent behavior between single- and multi-band adapters is a worse UX surprise than one extra click, and the handoff's wording ("Start Discovery stays disabled until a real band option... is picked") doesn't carve out an exception for the single-choice case.
- **Represent "unchosen" as `None` stored alongside the real choices in `self._band_choices`, rather than a sentinel label string excluded from the dict.** Rejected — `_band_choices` is looked up by `self._band_menu.get()`'s returned label; keeping the placeholder entirely out of that dict (rather than mapping it to `None`) means a future bug that forgets the gate check fails loudly (`KeyError`) instead of silently passing `bands=None` into `DiscoveryOptions`.

## Consequences

- **Re-verification against real hardware is required and NOT done in this session.** ADR-0013's own "What the real hardware showed" section is scoped to the *old* default/gating behavior (most-inclusive pre-selected, Start enabled once Idle) — it says nothing about a disabled-until-chosen Start button, which is new interaction surface, not new core behavior. This session has no real `sudo`/hardware access (`docs/roadmap.md`'s "Current state" constraints: no passwordless sudo, no TTY through Claude Code's inline shell), so this can't be closed here. **Flagging explicitly, per the handoff's own instruction**: the operator needs to drive the real Discovery & Targets page by hand once this lands — confirm the placeholder really can't be picked as a `DiscoveryOptions.bands` value, confirm Start truly can't be clicked before a real pick, and confirm the dual-band adapter (`wlx5c628b9faa9d`, phy3, per ADR-0013's own hardware notes) still reports both bands correctly once a real choice is made.
- **`docs/design/gui-structure.md`'s ADR-0013 amendment section and its state table need a follow-up note** once this lands, same as ADR-0013 itself amended ADR-0010's table in place rather than leaving it stale — not done as part of this ADR, since this ADR is scoped to the decision, not every downstream doc update (tracked in the redesign's own implementation checklist instead).
- **No behavior change for an adapter whose `supported_bands()` call fails** (`BandUnavailable`): `app.py`'s existing fallback to 2.4GHz-only still produces exactly one real choice, which point 5 above now makes clickable rather than permanently disabled — the operator still must click it once before Start enables, same as any other single-choice case.

## Implementation scope

- `aircommand/gui/app.py`: `_build_discovery_targets_tab`'s band-menu construction (placeholder entry, initial `.set()`, initial Start/New-Session `state`), a new `_on_band_menu_changed` handler wired as the menu's `command=`, and the `len(self._band_choices) > 1` → `>= 1` condition for the dropdown's own enabled/disabled state.
- Tests: `tests/test_app.py` — new cases asserting Start begins disabled, stays disabled while the placeholder is showing, enables on the first real pick (including the single-real-choice case), and that `DiscoveryOptions.bands` passed to `engine.discovery.start()` never includes a lookup against the placeholder label.
